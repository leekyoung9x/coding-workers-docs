Quy tắc:
- User gọi tên nào → dùng đúng worker + lệnh + combo đó. KHÔNG thay muse cho mini hay ngược lại. Tên model KHÔNG phải worker: user nêu model kèm worker thì giữ đúng họ worker, chọn model thật gần nhất trong họ đó hoặc hỏi lại — không lặng lẽ đổi sang worker khác.
- Mặc định ưu tiên mini worker số lượng lớn (bulk, song song); muse chỉ khi user gọi đích danh `muse-code` hoặc khi router mini (api.ai-box.vn qua 9Router 127.0.0.1:20127) chết kéo dài VÀ user đã duyệt fallback — router timeout thoáng qua thì giữ mini, retry, không tự ý chuyển.
- Khi Muse Code gặp lỗi Meta API 402 Billing verification failed / cạn hạn mức tài khoản Meta: báo rõ nguyên nhân tài khoản Meta và tự động fallback sang `mini` (`mini-swe-agent` với combo `thtung-paid`).
- Khi dispatch worker qua `wkctl launch` mà workspace `/poki` đang bị worker khác giữ lock (`preflight:workspace_lock`): dùng cờ `--no-workspace-lock` để chạy song song theo đúng chỉ đạo công việc bulk/parallel của user.
- Thư mục lưu brief: bắt buộc ghi vào `/poki/briefs/<TÊN_BRIEF>.md`, tuyệt đối không để ở root `/poki/` hay các thư mục test lẻ.
- Claude Code worker khi provider KHÔNG phải Anthropic (user đưa key của gateway khác): CLI gốc không nhận base URL tùy biến, nên `ANTHROPIC_API_KEY=<key gateway>` bị 401 `Invalid API key` vì CLI vẫn gọi `api.anthropic.com`. Cách chạy được: wrapper Python giả lập `claude -p` — đọc brief, POST sang Messages API của gateway, in JSON cùng shape `{type:"result", subtype, result, session_id, usage}` để lead parse như Claude thật; runner chỉ nhận đường dẫn brief + tên model. Chỉ dùng chế độ one-shot `-p`; interactive/tmux không dùng cho orchestration. Verify key bằng 1 request tối thiểu TRƯỚC khi dispatch — không verify thì brief chỉ treo hoặc trả rỗng.
- Nghi ngờ thì hỏi lại user trước khi spawn, không tự đoán.
- `thtung-paid` là COMBO CỦA MINI (DeepSeek), không phải model của muse.
- Tên worker là quyết định ROUTING (chọn lệnh), KHÔNG BAO GIỜ là tham số effort: `run_muse_worker.sh` chỉ nhận `none|minimal|low|medium|high|xhigh|max|ultra`. Truyền tên worker vào vị trí effort là lỗi cú pháp, worker không chạy.
- Muse `--yolo` bắt buộc khi chạy headless/background: khi chạy `muse exec` qua background process hoặc không có TTY/PTY tương tác, thiếu `--yolo` khiến các prompt xin quyền tích tụ đến giới hạn 32 (`capacity 32`) làm tiến trình crash ngay (`agent loop failed: model failed: model failed: pending approval state is full: capacity 32`). Luôn bắt buộc truyền `--yolo` trong mọi lệnh spawn headless của Muse.
- Mini key: KHÔNG dùng `mini-extra config set` (nó bọc value trong nháy đơn, mini gửi cả dấu nháy đi gây 401). Ghi file `~/.config/mini-swe-agent/.env` không nháy, hoặc export thẳng trong launcher (`OPENAI_API_KEY`/`LITELLM_API_KEY` + base `http://127.0.0.1:20127/v1` chung với Hermes).
- DeepSeek reasoning (mini) TẮT mặc định: 9Router combo `thtung-paid` báo `thinkingCanDisable: true` nên không gửi effort = chạy không reasoning. Bật max (`high`) bằng config override 2 lớp: `-c <mini.yaml> -c model.model_kwargs.reasoning_effort=high` — lớp đầu BẮT BUỘC (một `-c` đơn lẻ bỏ qua default config gây lỗi thiếu `system_template`/`instance_template`). Lấy `<mini.yaml>` động bằng đúng toolchain sẽ chạy worker (`/root/.hermes/bin/uvx --from mini-swe-agent python -c "import minisweagent, os; print(os.path.join(os.path.dirname(minisweagent.__file__), 'config', 'mini.yaml'))"`), KHÔNG hardcode `/root/.cache/uv/archive-v0/...` vì uv GC/update xóa archive cũ khiến path chết (cả symlink `~/.local/bin/mini` cũng có thể trỏ vào archive đã mất — khi đó chạy worker qua `uvx --from mini-swe-agent mini`, và cài lại để khôi phục symlink: `uv tool install mini-swe-agent`). Model gọi qua prefix `openai/` (`-m openai/thtung-paid`) như cột Lệnh chuẩn — dạng trần (`-m thtung-paid`) fail ngay `LLM Provider NOT provided`. Các cách nói `effect/mạnh nhất/cao nhất/xhigh` cho mini đều tính là yêu cầu rõ — bật reasoning high. Không có các từ đó thì giữ tắt — tốn token reasoning mỗi turn.
- DeepSeek Harness (`dsh`) headless & launching env: `dsh` cấm tuyệt đối đặt `DEEPSEEK_BASE_URL` trong file `.env` (lỗi `sets DEEPSEEK_BASE_URL, which only the launching environment may set; export DEEPSEEK_BASE_URL instead of putting it in a .env file`) — bắt buộc export trong script launcher. Để chạy tự động không bị prompt approval xin quyền, bắt buộc set `DSH_PERMISSION_MODE="danger-full-access"`. `dsh` giao tiếp qua chuẩn Anthropic Messages API (`/v1/messages`); patch model `thtung-paid` vào catalog `models` trong `~/.dsh/profiles/headless/cordis.patch.yml`. `dsh` nén session events dạng `zstd` trong `~/.dsh/sessions/` với token meter đo lường chi tiết (`inputTokens`, `outputTokens`, `totalTokens`), stream reasoning về stderr và kết quả cuối về stdout.
- Bắt buộc `--exit-immediately` cho mini trong orchestration: khi chạy `mini` tự động / headless, BẮT BUỘC truyền `--exit-immediately`. Thiếu cờ này, khi kết thúc task mini sẽ dừng lại ở prompt bàn giao tương tác `Agent wants to finish. Type new task or Enter to quit` khiến process không bao giờ thoát (treo vĩnh viễn).
- Đặc tính so sánh, điểm mạnh/yếu & tiêu chí định tuyến giữa các Worker khi chọn code (Tổng hợp từ Benchmark Vạn Kiếp Tu Tiên P1–P5 và thực chiến):
  * **Worker A (`@deepseek-ai/dsh` + DeepSeek V4.1 Flash):**
    - *Điểm mạnh:* Khả năng tự chủ và tự sửa lỗi (Self-healing) xuất sắc; khi gặp ca khó (i-frame kẹt test, đè lớp modal), tự viết file chẩn đoán `.dbg.mjs`, lần ra tận gốc vấn đề trong core engine và tự bổ sung API gỡ lỗi mà không cần Lead can thiệp. Bộ test chất lượng cao, chạy siêu tốc: 146 unit tests hoàn thành chỉ trong **1.02 giây**. Đồ họa UI Master-Detail và vector silhouette hoàn thiện không tì vết. Quy trình đóng gói tự động hóa 1 lệnh (`npm run verify`).
    - *Điểm yếu:* Tốn nhiều bước suy luận (826 steps qua 5 phase). Kích thước bundle lớn hơn (~500 kB JS). Đỉnh RAM cao hơn (~95.7 MB).
    - *Khi nào nên chọn code:* Xây dựng module lõi (Core Engine / Battle Logic phức tạp), dự án yêu cầu test coverage khắt khe chạy CI/CD tốc độ cao, hoặc cần UI hoàn thiện thương mại.
  * **Worker B (`mini-swe-agent` + DeepSeek V4.1 Flash):**
    - *Điểm mạnh:* Tiết kiệm bước và chi phí token số một: hoàn thành 5 phase chỉ với **564 steps** (ít hơn Worker A ~32%). Tốc độ thực thi chớp nhoáng (bugfix 20-34s). Sáng tạo mỹ thuật chữ Hán thư pháp (劍, 萬, 雷...) và văn phong tu tiên bản địa hóa xuất sắc kèm chú thích công thái học `(Restart)`, `(Về Menu)`. Bundle nhẹ (434 kB).
    - *Điểm yếu:* Tự chủ môi trường kém hơn (từng tự tạo `/tmp/p1`), chạy unit test chậm (19.3s do dính cảnh báo localStorage của Node), sót lỗi giao diện tràn thanh cuộn ở Bestiary.
    - *Khi nào nên chọn code:* Bugfix đơn file nhanh chóng, chạy song song số lượng lớn (bulk parallel tasks) để tiết kiệm token, và tác vụ vận hành DevOps/deploy script.
  * **Worker C (`opencode` + GLM-5.3-Flash):**
    - *Điểm mạnh:* Vô địch về tối ưu bundle và hiệu năng mô phỏng: bundle JS chính chỉ **344.6 kB** (gọn nhất trong tất cả các worker); thời gian mô phỏng mỗi step chỉ **0.0139 ms** (nhanh gấp 4.5 lần Worker A) nhờ cơ chế zero-allocation `compactInPlace`. Bộ test E2E Playwright sâu và phong phú nhất (23 bài test). Chi phí token GLM rẻ nhất.
    - *Điểm yếu:* Bắt buộc cấu hình cờ `--variant minimal` để tránh đụng trần 32k reasoning tokens của BigModel.
    - *Khi nào nên chọn code:* Ứng dụng frontend / Web Game nhạy cảm về kích thước bundle (budget < 350 kB), thuật toán mô phỏng toán học hiệu năng cao (Zero-GC), và viết test suite E2E bao quát sâu.
  * **Worker D (`agy` + Google Gemini 3.8 Flash):**
    - *Điểm mạnh:* Thẩm mỹ UI/UX hiện đại và đồ họa chiến đấu bóng bẩy nhất: thiết kế translucent glass container, vòng radar Bát Quái phân tầng biểu thị tầm đánh tự động, đạn đạo neon phát sáng rõ nét. Cửa sổ context siêu lớn (1M+ tokens). Tự động xoay tua 3 tài khoản Google OAuth chống lỗi 429.
    - *Điểm yếu:* Phụ thuộc vào cơ chế xác thực Google OAuth (keyring/interactive auth); bộ unit test bao quát vừa đủ theo brief (51 tests) chứ không tự viết dày đặc như A hay C.
    - *Khi nào nên chọn code:* Giao diện người dùng hiện đại, bóng bẩy (Commercial Indie Game, Landing Page, Dashboard cao cấp), refactor codebase đồ sộ nhồi toàn repo vào context, và tác vụ kết hợp đa phương thức (Multimodal mockup/video).
  * **Worker E (`muse` + Meta Muse Code — `muse-spark-1.3-contributor`):**
    - *Điểm mạnh:* Bố cục công thái học (HUD UX) khoa học nhất: dải thanh trạng thái ngang tinh tế ở đỉnh + Action Bar 6 ô chiêu thức ở đáy; tạo hình nhân vật Tu Sĩ mang đậm bản sắc văn hóa Việt Nam (nón lá truyền thống, áo đạo bào xanh ngọc). Tự phát hiện lỗi logic sâu trong vòng lặp game (tự bắt lỗi ticker ghi đè BGM mỗi frame khi vào Endless Mode). Tốc độ khung hình (FPS) mượt nhất toàn đoàn: đạt **59.9 FPS** trong headless Chromium, thời gian step 0.053 ms. Bundle JS đứng thứ 2 (**366.3 kB**).
    - *Điểm yếu:* Bắt buộc khóa cứng model `muse-spark-1.3-contributor` và cờ `--yolo` để tránh kẹt hàng đợi phê duyệt lệnh headless.
    - *Khi nào nên chọn code:* Xây dựng game/app cần vòng lặp frame tốc độ cao mượt mà (60 FPS), thiết kế giao diện đòi hỏi tư duy công thái học cao (HUD, Action Bar), và giải quyết các lỗi tương tác logic phức tạp trong game loop.

    - *Điểm mạnh:* Suy luận ngữ cảnh sâu và giải quyết thuật toán hóc búa, code review tỉ mỉ, bảo mật và rà soát lỗ hổng logic.
    - *Khi nào nên chọn code:* Code review trước khi commit/merge, điều tra bug logic khó hoặc tái cấu trúc thuật toán toán học phức tạp.
- Tương thích ngược constructor / API qua các phase: khi nâng cấp thực thể lõi qua các phase (như bổ sung `kind` vào `Boss`), bắt buộc dùng constructor overloading hoặc tham số tùy chọn (`new Boss(id, kindOrX, xOrY, y?)`) để các suite test cũ hoặc bộ chấm regression độc lập không bị gãy khi gọi signature cũ.
- Đo lường hiệu năng WebGL headless trên VPS không có GPU: Chromium headless trên Linux VPS không GPU chạy qua Google SwiftShader software rasterizer (`ANGLE SwiftShader Device (Subzero)`). Headless rAF trang trắng (`about:blank`) đạt 60 FPS, nhưng canvas WebGL có nhiều lớp alpha/geometry lớn trên CPU chỉ đạt ~15-30 FPS. Báo cáo benchmark phải đo baseline rAF trang trắng và ghi nhận rõ WebGL renderer info (`UNMASKED_RENDERER_WEBGL`) để phân biệt giới hạn phần cứng CPU với hiệu năng game thực tế trên GPU.
- Watchdog phải đo checkpoint và stage deadline, không suy luận treo chỉ từ log im/CPU tăng. Ghi PID/PGID + start fingerprint hoặc unit riêng khi launch; cleanup chỉ nhắm process được task sở hữu. CẤM broad `pkill -f` theo chuỗi trong brief (`Editor/Unity`, tên brief, port): mini truyền brief trong argv nên regex có thể chọn chính worker và shell gọi cleanup. Enumerate executable/ancestry trước khi gửi SIGTERM, grace có hạn rồi SIGKILL đúng phạm vi. Child exit không rõ nguyên nhân thì chẩn đoán trước; không respawn mù hoặc giết game live.
- Brief bắt chứng minh bằng 1 node mẫu khiến worker dừng sau mẫu và sót node khác. Bắt tool TỰ QUÉT full cây (không lấy mẫu, không gọi tay từng node) + test thêm node giả để khóa hành vi.
- Báo giao việc chỉ khi có bằng chứng thật: PID worker + job_id cron lấy từ output tool vừa chạy. CẤM nhắn 'đã giao' khi chưa có hai thứ này — báo khống mất niềm tin nhanh hơn mọi lỗi kỹ thuật.
- Router backend chết nhưng gateway vẫn trả 200: `curl /v1/models` 200 KHÔNG chứng minh backend sống. Sau chuỗi exit do ServiceUnavailable, chẩn đoán trước khi respawn mù: gọi chat completion thật tối thiểu qua 9Router, và đọc `journalctl -u 9Router` tìm account locked / backend 5xx. Respawn khi chưa rõ nguyên nhân chỉ đốt thêm lượt chết oan. NOTE: `journalctl -u 9Router` có thể rỗng (service không log journald) — khi đó probe bằng 3 chat completion thật cách nhau vài giây là nguồn diagnóstico chính.
- Verify brief còn nguyên sau khi ghi: brief vài trăm byte (chỉ còn tiêu đề) nghĩa là nội dung bị cắt — viết lại đầy đủ, đừng để worker bám tiêu đề đoán việc.
- Brief số liệu Figma cho worker: KHÔNG lấy từ output MCP rút gọn (`get_design_context` gộp gradient thành 1 màu solid, `get_metadata` bỏ hẳn strokes/fills). Lấy `type` + stops thật qua REST nodes API trước khi ghi số vào brief — số rút gọn khiến worker vẽ sai rồi đổ lỗi vòng quanh.
- Đo context thật của provider bằng payload tăng dần và so `usage.input_tokens` với ước lượng (text tiếng Anh ≈ 0.75 token/char). Lệch lớn = bị truncate âm thầm: XQ API chỉ nhận tối đa ~80K input tokens (đo được 80,081); payload 150K/271K chars chỉ còn 31K/75K tokens, KHÔNG báo lỗi, `content` rỗng. Trước khi tin con số context trên trang marketing của bất kỳ gateway nào, phải đo — không suy từ quảng cáo.
- Worker CLI tự cập nhật có thể ghi đè launcher/config đã chèn lock thủ công. Sau MỖI lần binary worker đổi version, kiểm lại lock (`grep -c <giá-trị-bị-khoá> <launcher>`, đối chiếu backup) rồi cài lại nếu mất, và luôn truyền model tường minh trong lệnh thay vì dựa vào lock. Kiểm luôn symlink của binary tự cập nhật/uv-cache (`ls -la ~/.local/bin/<worker>`) — symlink trỏ vào archive đã bị GC = worker chết âm thầm.
- Probe đúng COMBO sẽ dùng bằng 1 chat completion tối thiểu trước khi dispatch: các combo trên cùng một 9Router không cùng trạng thái (cùng lúc `thtung-paid` trả lời OK, `thtung-muse` trả `content: null` vì `reasoning_tokens` ăn hết budget, `thtung-glm` 403 hết quyền). `/v1/models` liệt kê combo với HTTP 200 KHÔNG chứng minh combo đó chạy. 9Router 127.0.0.1:20127 bắt buộc dùng đúng key `HERMES_CUSTOM_ROUTER_CUTES1TG_ONLINE_API_KEY` (đọc từ `/root/.hermes/.env`; curl với dummy key `sk-probe` sẽ bị từ chối `Invalid API key`). ## 5b — Cron watchdog ĐÃ CHỐT từ coding-workers-docs (nguồn sự thật)

Doc repo: `github.com/leekyoung9x/coding-workers-docs`, phần 5b — watchdog kèm mỗi worker là BẮT BUỘC, user không bao giờ phải hỏi 'xong chưa'. Quy tắc này không thay đổi trừ khi user sửa doc.

Tạo watchdog ngay cùng lượt dispatch, schedule `"every 3m"` theo yêu cầu hiện tại; không chờ user nhắc. Với job LLM pin `--model thtung-muse --provider custom:THTUNG` (hoặc model active như `thtung-agy`), `--workdir /poki`, skills cần thiết và delivery thread rõ ràng. Đọc `hermes cron create/edit --help` của phiên bản cài thực tế; dùng CLI cho model/provider pins, không sửa jobs.json hoặc giả định tool schema có trường chưa hỗ trợ. CẤM chỉ gọi tool `cronjob_manage(action="create")` mà quên pin model/provider: tool schema thiếu trường model/provider nên daemon sẽ fail ngay `RuntimeError: No LLM provider configured` và chết im lặng (khiến user phải hỏi 'sao không cắm cron'); nếu tạo qua tool phải gọi ngay `hermes cron edit --model <model> --provider <provider> --workdir /poki <job_id>` trong cùng lượt. No-agent script tick dùng cho trạng thái rẻ; verifier thức khi event/checkpoint thay đổi. Watchdog đối chiếu PID/start fingerprint + stage/deadline + artifact/hash, không pgrep nội dung brief. Completion chỉ IMPLEMENTED; có result mới thì re-run độc lập ngay, hai tick không checkpoint thì STALLED/chẩn đoán có hành động. Pause watchdog sau verdict cuối hoặc chuyển owner; giữ history và controller tiếp tục dependencies cho tới nghiệm thu toàn bộ. Cấm xóa giám sát chỉ vì worker exit0/self-report PASS. Kiểm job có trong list và lưu run ledger làm bằng chứng.
- Mini tool timeout 30s: tool bash của mini-swe-agent có timeout cứng 30s mỗi lệnh; các tác vụ nặng như `docker compose up -d --build`, `npm run build`, hoặc chạy Playwright screenshot / artifact capture đa viewport (`npm run artifacts`) chạy foreground sẽ bị TimeoutExpired. - Cron watchdog bằng `cronjob_manage(action="create")` tạo job xong phải pin model/provider NGAY TRONG LƯỢT TẠO hoặc bằng `hermes cron edit --model <model> --provider <provider> --workdir /poki <job_id>`: job create bình thường có model null và tick đầu chạy sẽ fail `RuntimeError: No LLM provider configured` và chết im lặng (chỉ thấy qua last_status error).
